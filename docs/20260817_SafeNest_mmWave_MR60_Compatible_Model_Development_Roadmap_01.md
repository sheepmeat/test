# SafeNest mmWave — MR60 호환 모델 개발 로드맵

- 작성일: 2026-08-17
- 문서 상태: **CURRENT ACTIVE MMWAVE MODEL-DEVELOPMENT ROADMAP**
- 대상: 프로젝트 리드, mmWave 담당, 모델 개발, 통합 엔지니어
- 범위: mmWave 모델 개발 순서만. CO₂ / Thermal / Pi 런타임 재설계 / 센서 보유자 실측 매뉴얼은 다루지 않는다.
- 성격: 실행 순서 문서. 이 문서를 쓰는 동안 데이터 처리, 학습, 수집, 모델 수정은 하지 않는다.

한 줄로 말하면:

```text
공개 110명 데이터의 사람 다양성 + 라벨
+
팀이 이미 찍어 둔 MR60 센서 domain
↓
둘을 잇는 새로운 호흡 표현을 비교·선택한다
↓
계약을 얼린 뒤 새 모델을 학습한다
↓
기존 MR60은 개발 참조 또는, 남을 때만, 제한된 held-out 확인
↓
정식 실기기 검증은 나중에 안 본 MR60 데이터로 한다
```

지금 허가된 다음 실행 단계는 **하나뿐이다.**

```text
M-N0 — 기존 팀 MR60 실측 전수조사
```

전처리, 학습, 신규 수집, INT8, Pi 통합은 아직 시작하지 않는다.

## 1. 왜 새 로드맵이 필요한가

기존 Phase B 모델은 공개 radar 데이터에서 복원한 **unwrap 위상(라디안)** 을 보고 학습됐다. 실제 SafeNest 런타임이 받는 값은 MR60BHA2 UART `0x0A13`의 vendor `breath_phase`다. 둘은 같은 숫자처럼 보여도 같은 신호가 아니다.

현재 권위 있는 판단은 다음과 같다.

```text
EXISTING_MMWAVE_B_LIVE_GATE = CLOSED
이유 = SIGNAL_CONTRACT_MISMATCH
```

이것은 Pi, ESP32, logger, TFLite 런타임이 깨졌다는 뜻이 아니다. **학습 입력과 실기기 입력의 신호 계약이 다르다**는 뜻이다.

그래서 앞으로는 기존 B 모델을 곱셈, 정규화, 보간, 이득 보정으로 살리지 않는다. 그렇다고 공개 110명 데이터를 버리고 새 MR60만 기다리지도 않는다. 공개 데이터는 사람 다양성과 지도학습 라벨이 있고, 팀 MR60 실측은 우리 센서 domain이 있다. 둘을 잇는 **새 입력 표현**을 만든 뒤 새 모델을 개발한다.

금지와 허용을 섞지 않는다.

```text
옛 B에 임의 스케일/정규화를 붙여 live에 맞추기  = 금지

새 모델의 표현으로 스케일-robust 정규화를 정의하고
TRAIN에만 맞춰 처음부터 학습하기              = 허용되는 연구
```

`TRAIN std / LIVE std` 같은 변환 계수, 옛 B 전용 정규화 해킹은 쓰지 않는다.

## 3. 무엇을 보존하고, 무엇을 멈추는가

### 보존 — 역사는 유효하다

- 완료된 Phase A (`M-A0`–`M-A6`)와 Phase B (`M-B0`–`M-B12`) 산출물
- 선택된 역사적 후보 `M-B3_CONV1D_GAP_BASELINE_seed42_M-B5_CAL_CLASS_BALANCED_120`
- INT8 SHA-256 `6dff6aaa72c79d76715d40cf7e32bb1e6cd9b2c2e3ac78eaf2fda737561430c5`
- 공개 110명 Zenodo 계보, subject-wise split 지식, A4 proxy 라벨 계약
- 팀이 이미 남긴 물리 MR60 JSONL/CSV와 실패 세션

기존 B 모델은 **VALID historical/offline artifact** 다. 지우거나 이름을 바꾸거나 전처리 계약을 고쳐 live에 맞추지 않는다.

### 정지 — 미래 실행 방향만 교체한다

이전 mmWave 미래 순서는 대략 이랬다.

```text
frozen B 후보
→ M-C0 대응 확인
→ M-C1 신규 실측
→ M-C2 frozen B의 정식 device 평가
→ 측정된 gap이 있을 때만 M-D
```

이 **미래 C/D 실행 방향**은 이제:

```text
PAUSED / SUPERSEDED FOR FUTURE EXECUTION
```

이유: M-C0/M-C2는 “기존 B 입력과 live `breath_phase`가 대응 가능한가”를 전제로 한다. 그 전제가 닫혔다. 완료된 A/B 연대기는 다시 쓰지 않는다. 이전 실행 순서 문서는 역사·세부 근거로 남긴다.

- [기존 mmWave A–E 실행 순서](20260806_ChatGPT_SafeNest_mmWave_Execution_Sequence_01.md) — A/B 역사는 유효, 미래 C/D는 이 문서에 양보
- [멀티센서 master roadmap](20260810_ChatGPT_SafeNest_Multisensor_Parallel_Execution_Roadmap_01.md) — CO₂/Thermal/통합은 유지, mmWave 미래 모델 경로는 이 문서

### 단계 이름

완료된 `M-A` / `M-B` 번호를 바꾸지 않는다. 이전 `M-C` / `M-D`도 역사적 이름으로 남긴다.

새 미래 단계는 **`M-N0`–`M-N12`** 다. `M-`는 mmWave 트랙, `N`은 2026-08-17 이후의 새 모델 계보다. 이전 M-C0 “frozen B 대응 감사”와 새 M-N0 “실측 전수조사”를 같은 일로 부르지 않는다.

새 모델 이름은 기존 B 후보명과 겹치지 않게 한다. 개념적으로 `MR60_COMPAT_...` 또는 저장소 관례에 맞는 새 identity를 쓴다.

원칙은 이것이다.

```text
탐색 → 비교 → 선택 → 동결
```

동결한 뒤에 창과 전처리를 고르지 않는다.

## 4. 기존 팀 MR60을 개발 데이터와 평가 데이터로 나눈다

기존 팀 MR60은 한 덩어리로 “학습에도 쓰고 검증에도 쓴다”고 말하지 않는다.

```text
EXISTING_TEAM_MR60
        │
        ├── MR60_DEVELOPMENT_REFERENCE
        └── MR60_HELDOUT_REFERENCE   (의미 있게 남길 수 있을 때만)
```

**MR60_DEVELOPMENT_REFERENCE**
공통 표현, 타이밍/창, 전처리, 분포, 탐색적 모델 개발을 볼 때 열 수 있다. 한 번 그런 결정에 쓰이면 그 세션은 개발 증거다.

**MR60_HELDOUT_REFERENCE**
표현, 정규화, 창, 필터, 구조, 임계값, 적응 전략을 고르는 데 쓰지 않는다. 적합한 세션이 충분히 남을 때만, 나중에 제한된 held-out 확인에 쓸 수 있다.

피험자·독립 라벨·세션 다양성이 부족하면 **모양을 위해 held-out을 만들지 않는다.** 그때는 적합한 기존 MR60을 모두 개발/참조로 쓰고, 이후 단계는 이름을 이렇게 부른다.

```text
EXPLORATORY_DEVICE_DOMAIN_CHECK
```

명시할 문장:

> 기존 팀 MR60이 개발 결정에 참여했다면, 그 데이터는 독립적인 정식 검증셋이 아니다.

**FORMAL_REAL_DEVICE_VALIDATION** 은 미래 실측에 남긴다. 조건은 대략:

- 새롭거나 안 본 세션
- 가능하면 안 본 사람
- 타깃에 맞는 독립 참조
- 표현/학습/튜닝/적응에 쓰지 않음

기존 팀 MR60이 할 수 있는 일은 domain 적합성 분석, 탐색적 device check, 정말 남겨 둔 경우에만 제한된 held-out이다. “최종 MR60 일반화가 증명됐다”는 기존 개발 참여 데이터로 말하지 않는다.

팀 MR60이 자동으로 TRAIN에 들어가지도 않는다. 공개 110명 + 팀 MR60 전체를 한 학습셋으로 합치지 않는다. 각 세션 역할은 M-N1이 정한다.

최근 Pi/런타임 캡처의 초기 역할은 **`RECENT_PI_RUNTIME_REFERENCE`** 다. 숫자 범위, cadence/타이밍, 런타임 소스 행동, 입력 분포, 파이프 확인용이다. 독립 근거가 확인되기 전에는 지도학습도, 정식 검증도 아니다.

## 5. 단계 한눈에 보기

각 단계는 보통 **질문 하나, 산출물 하나, gate 하나**다. 추가 산출물은 구체적인 실패를 막을 때만 만든다. 역사적 A/B가 validator를 많이 썼다고 같은 양을 요구하지 않는다.

보통이면 이것으로 충분하다.

```text
구현 또는 분석 하나
+ 결과 표/플롯 하나
+ 짧은 결정 요약
+ 필요한 최소 확인
```

| Phase | 핵심 질문 | 주요 작업 | 주 산출물 | 다음 단계 Gate |
|---|---|---|---|---|
| **M-N0** | 이미 찍힌 MR60이 어디에 있고 무엇인가? | 기존 보고 우선, 모호할 때만 원본 | 인벤토리 한 장 | 세션마다 역할 후보를 붙일 수 있는가 |
| **M-N1** | 그 데이터를 학습에 넣어도 되는가? | 라벨·참조 감사 | 세션별 ML 용도 한 표 | 순환 라벨 없이 용도가 정직한가 |
| **M-N2** | 공개 데이터와 MR60을 잇는 표현이 있는가? | 소수 표현 비교 | 비교 표 + 결정 요약 | 공개 예측력과 MR60 동작이 둘 다 납득되는가 |
| **M-N3** | 타이밍·창·전처리는 무엇을 쓰는가? | 소수 옵션 비교 | 선택 결과 한 줄 | TRAIN-only로 재현 가능하고 개발용 MR60만 봤는가 |
| **M-N4** | 새 입력 계약을 얼릴 수 있는가? | N0–N3 답을 계약으로 고정 | canonical 계약 하나 | 추측을 얼리지 않았는가 |
| **M-N5** | 작은 모델로 학습되는가? | 선형 / Conv1D / Conv1D+GAP | 학습 후보 | 과한 탐색 없이 후보가 생겼는가 |
| **M-N6** | 공개 데이터에서 무엇을 고르는가? | VAL로 선정, 새 held-out은 1회 | 선정 기록 + NEW_MODEL_HELDOUT_TEST | 선정에 held-out을 쓰지 않았는가 |
| **M-N7** | 기존 MR60에서 어떻게 보이는가? | 남겨 둔 세션만 held-out, 아니면 탐색 | 탐색 또는 제한 held-out 기록 | 개발 참여 데이터로 정식 검증을 주장하지 않았는가 |
| **M-N8** | 측정된 구멍이 있어 적응이 필요한가? | 필요할 때만 소량 적응 | 적응 여부 기록 | 구멍 없이 적응하지 않았는가 |
| **M-N9** | 최종 float를 INT8로 올리고 Pi에서 도는가? | 적응 동결 후 FULL_INT8 | PI_INFERENCE_READY | 아직 바뀔 float를 양자화하지 않았는가 |
| — | **센서 접근 게이트** | 여기까지는 기존 증거로 진행 | — | 신규 수집이 N0–N9를 막지 않는가 |
| **M-N10** | 부족한 증거만 요청하면 되는가? | 앞 단계 gap으로 요구사항 전달 | 수집 요구 목록 | 센서 보유자에게 절차를 중복하지 않았는가 |
| **M-N11** | 안 본 실측으로 일반화되는가? | 학습/튜닝에 안 쓴 미래 MR60 | FORMAL_REAL_DEVICE_VALIDATION | Pi 실행을 검증 완료로 쓰지 않았는가 |
| **M-N12** | 최종 구멍이 남는가? | 필요할 때만 통제된 보정 | 릴리스 판단 | 최종 검증셋으로 계속 튜닝하지 않았는가 |

## 6. M-N0 — 기존 팀 MR60 실측 전수조사

**왜 하는가.**
지금 가진 물리 데이터를 모르면, 학습에 넣을지 / 적응에만 쓸지 / 실패 증거인지를 정할 수 없다.

**실제로 무엇을 하는가.**
이것은 또 하나의 M-C0 forensic이 아니다. 질문은 하나다. **어떤 팀 MR60 녹음이 있고, 각각이 무엇인가?**

이미 믿을 수 있는 2026-08-14 평가를 먼저 쓴다. 중요한 모호함이 있을 때만 원본을 연다. 모든 통계를 다시 계산하지 않는다.

2026-08-14 평가가 **출발 가설**로 가리키는 예는 아래와 같다. 목록이 완전하다고 가정하지 않는다.

| 알려진 후보 | 대략적 조건 | M-N0에서 확인할 것 |
|---|---|---|
| `S001_NORMAL_D06` / `D09` | 재실, 거리 조건 | 원본 경로, 신선도 메타, 사용 가능 역할 |
| `S001_NORMAL_D12` | presence drop 가능성 | 실패/QA로 둘지 |
| `S001_NORMAL_D15` | freeze / lock-loss | 실패/QA로 둘지 |
| paced 12 / 15 / 20 rpm | 지시 호흡, 실패·shallow·deep 포함 | cue ≠ 생리 정답 |
| ~31분 D09 JSONL | 장시간, stale phase 증거 | 타이밍/QA |
| PR18 Pilot Desk-work / Stationary | 캡처 도구 다른 세션 | 레거시와 합치지 말 것 |
| 2026-08-17 Pi JSONL (`data/mmwave/20260817_08_mmwave.jsonl` 등) | `RECENT_PI_RUNTIME_REFERENCE` | 라벨 없으면 학습/정식 검증으로 올리지 말 것 |
| 그 외 미요약 물리 측정 | 미상 | 찾아서 빠짐없이 적기 |

세션마다 이 칸이면 충분하다. 두 번째 증거 장부를 만들지 않는다.

| 칸 | 뜻 |
|---|---|
| Session / bundle ID | 세션 정체 |
| Repository path | 원본 위치 |
| Subject | 알면 `S001` 등 |
| Condition | 재실 / paced / 정지 / 실패 등 |
| Duration | 대략 |
| Signal available | `breath_phase` / 기타 |
| Freshness evidence | `phase_age_ms` / 직접 identity / 없음 |
| Reference | 독립 참조 / paced cue / 없음 |
| Label confidence | high / medium / weak / unavailable |
| Known issue | freeze / presence loss / 저진폭 등 |
| Recommended use | 학습 / 적응 / 개발 참조 / held-out 후보 / QA / 제외 |

**무엇이 나오면 끝나는가.**
인벤토리 한 장과 짧은 해석.

**다음으로 못 가는 경우.**
원본과 파생을 구분하지 못했거나, 빠진 묶음을 “없다”고 단정한 경우. 이 단계에서 Accuracy나 학습을 시작하면 실패다.

## 7. M-N1 — 학습 가능 여부와 라벨 감사

**왜 하는가.**
파일이 있다고 정답이 있는 것은 아니다.

**실제로 무엇을 하는가.**
세션을 아래 중 하나로만 분류한다. 라벨 manifest를 여러 벌 만들지 않는다.

```text
SUPERVISED_TRAINING_ELIGIBLE
WEAKLY_LABELED_OR_ADAPTATION_CANDIDATE
DEVICE_DOMAIN_REFERENCE
FAILURE_OR_QA_EVIDENCE
RECENT_PI_RUNTIME_REFERENCE
NOT_RECOMMENDED_FOR_MODEL_USE
```

특히 지키면 안 되는 것:

```text
paced 12/15/20 rpm  ≠  검증된 호흡 정답
paced cue           ≠  독립 측정 호흡
MR60 breath_rate_raw ≠  독립 정답
같은 MR60 호흡수로 같은 MR60 모델을 채점·학습
```

paced 세션은 버릴 필요가 없다. 주기 특성, 공통 표현 비교, 약한 라벨/적응 연구에 쓸 수 있다. 자신감만 정직하게 적는다. APNEA는 독립 참조가 없으면 임상 주장이 아니라 proxy/비임상이다.

가능한 학습 전략은 N1 **이후**, 실제로는 M-N4 동결에서 고른다. 지금 하나를 고정하지 않는다.

| 전략 | 공개 110명 | 팀 MR60 |
|---|---|---|
| A | 지도학습 | 학습에 넣지 않음. 표현/domain 분석만 |
| B | 지도학습 | `SUPERVISED_TRAINING_ELIGIBLE`만 추가 학습 |
| C | 사전학습 | 적합한 세션만 fine-tune |
| D | 지도학습 | 표현/domain 분석 + 개발 참조. 검증 주장 없음 |

A가 “공개만 학습”이고, 예전 초안의 B(검증만)와 섞지 않는다. 기존 MR60을 정식 검증셋으로 쓰기 위해 전략을 고르지 않는다.

**무엇이 나오면 끝나는가.**
세션별 용도 한 표. 개발 참조로 쓸 세션과, 정말 남길 held-out 후보가 있는지도 이 표에 표시한다. 데이터가 모자라면 held-out 후보는 비워 둔다.

**다음으로 못 가는 경우.**
순환 라벨을 만들었거나, 실패 세션을 정상 학습 예제로 승격한 경우.

---

## 8. M-N2 — 공개 데이터와 MR60의 공통 표현

**왜 하는가.**
원시 위상 단위가 다르다. 호흡의 시간 모양은 양쪽에서 남을 수 있다. 이 단계가 새 트랙의 핵심 연구다.

**실제로 무엇을 하는가.**
후보는 처음에 셋 또는 넷. 승자를 로드맵에서 미리 고르지 않는다.

1. 중심화/디트렌드 파형
2. delta / 미분 위상
3. 호흡대역 + 스케일-robust 정규화 (새 계약. 옛 `BPF_ZSCORE` 패치 아님)
4. 작은 스펙트럼/시간 특징 — 필요하면 한 묶음만

비교는 둘 다 본다.

- **공개 도메인:** 지도학습 정보가 남는가
- **MR60 도메인:** 숫자가 폭발하지 않는가, 호흡 주기가 보이는가, 세션 간 해석이 가능한가, 문서화되지 않은 절대 스케일에 지배되지 않는가, 실제 타이밍을 견디는가

보는 MR60은 **개발 참조**만. 남겨 둔 held-out이 있으면 여기서 열지 않는다.

탐색은 플롯, PSD, 자기상관, 분포, 대표 세션, paced 비교로 충분하다. 통계마다 영구 validator를 만들지 않는다.

**무엇이 나오면 끝나는가.**
비교 표와, 채택 또는 탈락 이유 짧은 요약. 아직 한 표현으로 못 줄이면 최대 둘을 N3로 넘긴다.

**다음으로 못 가는 경우.**
원시 두 도메인을 이어 붙였거나, 공개 성능만 보고 고른 경우, 또는 옛 B에 임의 스케일을 붙인 경우.

---

## 9. M-N3 — 타이밍·창·전처리 선택

**왜 하는가.**
표현 가족을 본 뒤에야 창과 전처리를 고른다. 계약을 먼저 얼리고 나중에 비교하지 않는다.

**실제로 무엇을 하는가.**
옛 B 계약(`10 Hz / 300 / 30 s / BPF_ZSCORE`)은 역사에 남긴다. 자동 상속하지 않는다. 과한 타이밍 설계도 하지 않는다. 개발용 MR60과 공개 TRAIN/VAL만 보고 소수 옵션을 비교한다.

```text
창: 고정 시간 / 고정 샘플 수 / 이유가 있을 때만 고정 cadence 리샘플
전처리: 고른 표현 그대로 / 가벼운 디트렌드 / 단순 호흡대역 / delta
정규화: 필요할 때만 TRAIN-only 전역 통계
```

세 시각은 구분하되, 또 한 번의 대형 forensic은 하지 않는다.

```text
MR60 소스 phase 갱신
ESP 텔레메트리
Pi 수신
```

통계는 TRAIN에만 맞춘다. VAL/TEST와 MR60 held-out에 맞추지 않는다.

**무엇이 나오면 끝나는가.**
선택한 타이밍·창·전처리 한 줄과 짧은 근거.

**다음으로 못 가는 경우.**
옛 `BPF_ZSCORE`를 “일단 그대로” 가져온 경우, 또는 탐색 격자가 모델 선정보다 커진 경우.

---

## 10. M-N4 — canonical 입력·데이터 전략 동결

**왜 하는가.**
N0–N3가 답을 준 뒤에만 계약을 닫는다. 단계가 있다고 추측을 얼리지 않는다. 아직 못 정하면 명시적 blocker로 남기고 N5로 가지 않는다.

**실제로 무엇을 하는가.**
아래가 닫혀야 동결이다.

```text
모델 타깃
canonical 표현
소스 신호
타이밍 기준
창 정의
리샘플 여부
전처리
정규화
공개 데이터 사용법
MR60 데이터 사용법 (전략 A–D)
라벨 정책
split 정책
개발 참조 / held-out 참조 분리, 또는 held-out 불가 선언
```

**타깃.** 역사적 3-class를 자동 유지하지 않는다.

| 옵션 | 언제 주력으로 쓰는가 |
|---|---|
| `NORMAL` / `RAPID_OR_ABNORMAL` / `APNEA` proxy | 공개 라벨을 새 표현에 방어 가능하게 옮길 수 있을 때 |
| 호흡수 회귀 | 독립 정답이 분류보다 더 단단할 때 |
| 신호 품질 게이트 | 나쁜 MR60 창을 거르는 보조. 주력 모델을 대체하지 않음 |

권고: **주력 하나 + 보조 품질 게이트 최대 하나.** APNEA는 계속 비임상 proxy다.

**공개 split.** 110명 데이터는 이미 역사적 A/B에 쓰였다. 새 표현 때문에 창을 다시 만들면 **새 derived track** 을 만들고, 가능하면 새 subject grouping을 후보 선정 **전에** 고정한다. 이것이 프로젝트 전체가 한 번도 안 본 사람 집합이라는 뜻은 아니다. 이름은 **`NEW_MODEL_HELDOUT_TEST`** 다. 역사적 B `LOCKED_TEST`를 다시 열어 새 표현을 고르지 않는다. 옛 B 점수를 새 모델 점수로 복사하지 않는다. 새 grouping이 방어 불가능하면 그 한계를 계약에 적는다.

**무엇이 나오면 끝나는가.**
새 모델 입력 계약 하나. 역사적 B 계약은 수정하지 않는다.

**다음으로 못 가는 경우.**
전략이 N1과 모순되거나, 미결정 상수를 추측으로 얼린 경우.

---

## 11. M-N5 — 새 후보 학습

**왜 하는가.**
목표는 장치에서도 버틸 단순한 모델이다.

**실제로 무엇을 하는가.**
초기 후보는 이 정도면 된다.

1. 단순 특징 / 선형 baseline
2. 작은 Conv1D
3. Conv1D + GAP

N2–N4가 이유를 줄 때만 가벼운 시간 모델을 하나 더 넣는다. 아키텍처 탐색, 대형 transformer/RNN은 하지 않는다.

학습 데이터는 N4 전략을 따른다. 팀 MR60 전체가 자동으로 TRAIN이 되지 않는다. 센서가 없다고 이 단계를 멈추지 않는다. 공개 데이터와, N1에서 허가된 MR60만 쓴다.

**무엇이 나오면 끝나는가.**
작은 후보군과 TRAIN/VAL 기록. `NEW_MODEL_HELDOUT_TEST`로 고르지 않는다.

**다음으로 못 가는 경우.**
기존 B 가중치를 이어 받아 “새 모델”이라고 부르거나, 무관한 트랙 코드를 섞은 경우.

---

## 12. M-N6 — 오프라인 선정과 새 모델 held-out

**왜 하는가.**
사람 다양성은 공개 데이터에 있다. 선정과 최종 확인을 같은 집합에서 하지 않는다.

**실제로 무엇을 하는가.**

```text
TRAIN            → 맞춤
VALIDATION       → 표현/모델/하이퍼파라미터 선택
NEW_MODEL_HELDOUT_TEST → 얼린 후보만 평가
```

held-out으로 구조, 전처리, 임계값, class weight, 창, 표현을 고르지 않는다. 분류면 Macro F1, 클래스별 recall, confusion. 회귀면 MAE/RMSE와 오차 분포. 모델 크기와 추론 단순함. 복잡한 랭킹 프레임워크는 만들지 않는다.

이 held-out은 **새 파이프라인의 규율**이다. SafeNest가 해당 피험자를 한 번도 본 적 없다는 전역 주장이 아니다. 역사적 B `LOCKED_TEST`와 이름을 섞지 않는다.

**무엇이 나오면 끝나는가.**
선정된 float 후보와, 그 후보의 `NEW_MODEL_HELDOUT_TEST` 기록 한 번.

**다음으로 못 가는 경우.**
역사적 B locked-test를 새 점수로 썼거나, held-out으로 후보를 고른 경우.

---

## 13. M-N7 — 기존 MR60 탐색 / 제한 held-out

**왜 하는가.**
공개 데이터에서 좋아도 우리 센서에서 붕괴하면 안 된다. 그렇다고 기존 실측만으로 최종 일반화를 주장하지도 않는다.

**실제로 무엇을 하는가.**
M-N1에서 정말 남겨 둔 `MR60_HELDOUT_REFERENCE`가 있으면, 그 세션만 제한된 device held-out으로 보고 라벨 한계를 같이 적는다.

그런 세션이 없으면 단계 이름은:

```text
EXPLORATORY_DEVICE_DOMAIN_CHECK
```

개발에 쓴 세션으로 출력 붕괴, 세션 안정, 분포 이동, 주장 가능한 경향만 본다. 무라벨 데이터에 Accuracy/F1을 만들지 않는다. 실패 세션은 QA로만 본다.

어느 경우에도 이 단계의 결론은 **FORMAL_REAL_DEVICE_VALIDATION 이 아니다.**

**무엇이 나오면 끝나는가.**
탐색 기록, 또는 제한 held-out 기록. 개발 참여 여부를 한 문장으로 밝힌다.

**다음으로 못 가는 경우.**
개발에 쓴 세션으로 “최종 MR60 일반화”를 말한 경우.

---

## 14. M-N8 — 구멍이 측정됐을 때만 적응

적응은 기본값이 아니다. N7에서 납득되면 건너뛴다.

구멍이 보이면 그때만, N1에서 해당 방법에 맞는 **개발 허가 세션만** 써서 단순한 방법부터 한다.

- 적합한 MR60 fine-tune
- 혼합 도메인 학습
- 제한된 재보정

큰 domain-adaptation 연구를 기본으로 두지 않는다. 약한 라벨을 강한 라벨처럼 쓰지 않는다. held-out MR60이 있으면 적응 선택에 쓰지 않는다.

N8이 모델을 실질적으로 바꾸면, 그 float를 다시 동결한 뒤에만 N9로 간다.

---

## 15. M-N9 — FULL_INT8과 Pi 추론 준비

**최종 float 파이프라인이 멈춘 뒤에만** 한다. N6에서 고른 후보가 N8에서 바뀌면, 바뀐 float를 동결한 다음 양자화한다.

필수 확인만 한다.

- 변환 성공
- 입출력 텐서 계약
- 보정 예제는 TRAIN 유래
- float 대비 성능 저하가 납득됨
- 심한 saturation 없음
- Pi가 로드/실행 가능

이 단계의 통과 이름은 **`PI_INFERENCE_READY`** 다. **`DEVICE_VALIDATED` 가 아니다.** 변환만으로 배포 준비를 주장하지 않는다. 양자화 대감사는 문제가 보일 때만 한다.

이 단계가 끝나도 **mmWave live gate는 열지 않는다.** 이 로드맵에서 Pi 런타임·펌웨어를 수정하지 않는다.

---

## 16. 센서 접근 게이트

N0–N9는 기존 공개 데이터와 기존 팀 MR60으로 한다. 센서가 당장 없다고 모델 작업을 멈추지 않는다.

이후 신규 물리 접근의 목적은 더 많이 찍는 것이 아니라, 앞에서 측정된 구멍을 메우는 것이다. 정식 검증은 여기서부터다.

```text
PI_INFERENCE_READY
≠
FORMAL_REAL_DEVICE_VALIDATION
```

---

## 17. M-N10 — 구멍에 맞는 신규 수집 요구

이 단계는 측정 매뉴얼이 아니다. 모델 쪽이 센서 보유자에게 **부족한 증거만** 요청한다.

앞 단계 적자의 예:

- 사람이 너무 적다
- 독립 참조가 없다
- 거리마다 표현이 흔들린다
- 특정 클래스가 없다
- MR60 적응 구멍이 남는다
- 특정 실패 조건이 없다

요청에는 왜 필요한지, 독립이어야 하는 증거, subject/session identity, 원본 보존이 들어가면 된다. 어떻게 찍는지는 실측 안내서와 센서 보유자 로드맵에 맡긴다. 큰 실험 행렬을 만들지 않는다.

**무엇이 나오면 끝나는가.**
수집 요구 목록 하나. 현장 절차 복제본이 아니다.

---

## 18. M-N11 — 정식 실기기 검증

여기서야 비로소 말할 수 있다.

```text
FORMAL_REAL_DEVICE_VALIDATION
```

조건: 학습/튜닝/표현 선택/적응에 쓰지 않은 실제 MR60, 가능하면 새 사람, 선택한 타깃에 맞는 독립 참조.

```text
PI_INFERENCE_READY     ≠  DEVICE_VALIDATED
모델이 Pi에서 돌아간다 ≠  실제 MR60 domain에서 검증됐다
```

---

## 19. M-N12 — 필요할 때만 최종 보정

N11에서 측정된 구멍이 있으면 별도 통제된 보정만 한다. 최종 검증셋으로 계속 튜닝하지 않는다. 구멍이 없으면 추가 학습을 만들지 않는다. 여기서 float가 바뀌면 INT8도 다시 한다.

---

## 20. Lean Validation Policy

대부분의 노력은 여기 쓴다.

```text
실제 데이터
신호 이해
전처리
모델링
device-domain 확인
```

검증 기계를 키우는 데 쓰지 않는다. 검증은 **실제 실패 모드를 막을 때만** 둔다.

느슨한 ML이 아니다. 아래는 빼지 않는다.

- subject / session 누수
- 라벨 누수
- TRAIN/VAL/TEST 오염
- TRAIN 밖 데이터로 scaler/정규화 맞추기
- 원본 실측 변조
- 모델 아티팩트 identity 상실

기본으로 요구하지 않는 것:

- 저장소 전체 재감사 반복
- 같은 내용의 보고서·장부 여러 벌
- 중간 통계마다 별도 manifest
- 탐색 통계용 영구 validator
- 무관한 센서 테스트
- 실험 단계마다 checksum 재생성
- 완료된 A/B 증거를 다시 증명

탐색 질문은 플롯/표로 답하면 된다. **canonical 모델 계약이 되는 것만** 정식화한다.

테스트는 침묵한 구현 오류가 모델을 오염시킬 곳에만 둔다. 표현/전처리 구현, split 누수, 라벨 매핑, 텐서 계약, 최종 데이터셋 결정성, Pi 추론. 문장이나 메타데이터 칸마다 테스트하지 않는다.

## 21. Git 격리

mmWave 전용 브랜치에서만 작업한다. 단계 시작/끝에 이 정도면 충분하다.

```bash
git fetch origin
git status --short
git log origin/main..HEAD --oneline
git diff origin/main...HEAD --name-only
```

워킹트리가 깨끗해도, `origin/main`에 없는 CO₂ / Thermal / Integration 커밋이 브랜치에 있으면:

```text
PARALLEL_TRACK_BRANCH_CONTAMINATION
```

한 단계 안에서 같은 확인을 반복하지 않는다. 기존 A6 canonical, 옛 split ID, 옛 라벨, 옛 B 지표, 옛 B `LOCKED_TEST`는 덮어쓰지 않는다. 새 계보는 새 산출물을 만든다.
