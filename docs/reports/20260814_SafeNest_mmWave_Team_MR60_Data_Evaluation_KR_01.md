## 1. 결론부터

**지금 팀 MR60 데이터는 버릴 데이터가 아닙니다.**
실제 센서가 무엇을 남기는지 보는 데는 충분히 가치가 있습니다.

다만 **지금 당장 모델 성적표(Accuracy, F1)를 내거나, 그 로그로 바로 재학습하면 안 됩니다.**

한 줄로 말하면:

```text
입력 X(센서 신호)는 있다
정답 y(Phase-B 클래스)는 아직 충분하지 않다
```

그래서 순서는 이렇습니다.

```text
센서/domain 분석 (지금, M-C0)
        ↓
입력 신호가 기존 모델 입력과 같은 뜻인지 확인
        ↓
맞을 때만 탐색적 추론
        ↓
그다음 규약 있는 새 실측 (정답을 신호와 같이 기록)
        ↓
정식 평가
        ↓
실제 차이가 확인되고 따로 승인된 뒤에만 재학습
```

## 2. 지금 팀이 가지고 있는 데이터는 쓸 만한가?

쓸 만합니다. 다만 **용도가 다릅니다.**

이미 있는 것:

- 실제 MR60BHA2 물리 측정
- 시각이 찍힌 JSONL 로그와 CSV
- `breath_phase`와 vendor `breath_rate_raw`
- 12 / 15 / 20 rpm paced 호흡 시험
- 거리 조건 (D06 / D09 / D12 / D15)
- 실패한 세션을 지우지 않고 남긴 기록
- 약 31분 schema 1.2 로그

아직 없는 것:

- 여러 사람으로 확인된 다양성 (전달 CSV 기준 식별 가능한 사람은 `S001`)
- 호흡 벨트/스파이로미터 같은 독립 호흡 정답
- 기존 Phase-B 모델이 기대한 입력과 `breath_phase`가 같은 신호라는 증명
- 로그가 약 10 Hz로 찍힌다는 사실이, 매번 새로운 phase 샘플이라는 증명

판정:

```text
센서 분석 / M-C0용:     가치 있음
정식 모델 검증용:       아직 아님
바로 재학습용:          아직 아님
```

## 3. 현재 데이터에서 잘 된 부분

칭찬할 점은 실제로 파일로 남아 있습니다.

- 측정 시각을 남겼습니다. 나중에 “몇 Hz였나”를 계산할 수 있습니다.
- phase 비슷한 파형과 vendor 호흡수를 **둘 다** 저장했습니다. 그래서 둘이 다르다는 것을 볼 수 있습니다.
- 12 / 15 / 20 rpm을 시도했고, 12 rpm이 실패하자 다시 쟀습니다.
- 거리 조건도 여러 번 시도했습니다.
- 실패 세션을 삭제하지 않았습니다. 잘못된 12 rpm, 얕은 20 rpm, D15 freeze가 남아 있습니다.
- CSV와 원본 JSONL의 SHA-256이 매니페스트에 있습니다.
- 내보낸 `resp_phase`를 임의로 정규화하거나, 사람 없을 때 가짜 값을 채워 넣지 않았습니다.

즉, “대충 적어 둔 메모”가 아니라 **다시 열어볼 수 있는 실측 기록**입니다.

## 4. breath_phase와 breath_rate_raw는 무엇이 다른가?

이 구분이 가장 중요합니다.

펌웨어 (`devices/mmwave/firmware/src/main.cpp`):

```text
0x0A13  →  totalPhase, breathPhase, heartPhase
           JSON의 breath_phase

0x0A14  →  breathRaw
           JSON의 breath_rate_raw  (vendor 호흡수)
```

**`breath_phase`**
가슴 움직임과 관련된, 장치가 지금 내보내는 가장 낮은 수준의 phase-like 중간 신호입니다.
기존 AI 입력과 비교할 **후보**입니다.
그렇다고 해서 레이더 ADC/IQ/원본 range-FFT라고 확인된 것은 아닙니다.
지금 팀 로그에서 그런 배열은 보이지 않습니다.

**`breath_rate_raw`**
센서 업체가 계산해 내보내는 호흡수입니다.
AI가 보는 파형이 아닙니다.
이 숫자를 모델 입력처럼 쓰면 안 됩니다.

## 5. 약 10 Hz라고 해서 바로 AI 입력 10 Hz라는 뜻은 아닌 이유

여러 세션의 JSONL/CSV **행 간격**은 약 **9.99 Hz**입니다.
최대 행 간격은 약 101–103 ms입니다. 이 부분은 확인됐습니다.

하지만 펌웨어는 이렇게 동작합니다.

- JSON 로그는 약 100 ms마다 찍힙니다 (`kTelemetryIntervalMs = 100`).
- `breath_phase` 값은 `0x0A13` phase frame이 **들어올 때만** 갱신됩니다.
- 로그는 그 사이 **마지막 값을 다시 출력**할 수 있습니다.
- `phase_age_ms`가 바로 “이 값이 얼마나 오래됐는지”를 적는 필드입니다.

그래서:

```text
로그가 1초에 약 10줄 찍힘
≠
breath_phase가 1초에 10번 새로 갱신됨
```

31분 로그가 이 차이를 직접 보여 줍니다.
행 cadence는 9.986 Hz인데, `phase_age_ms` 최대는 **288,530 ms**이고
30초보다 오래된 phase 행이 **2,585개**입니다.
로그는 계속 찍히는데 phase는 수분 동안 안 바뀌었을 수 있습니다.

30초 동안 약 300줄을 자를 수는 있습니다.
그 300줄이 **새로운 phase 샘플 300개**인지는 아직 M-C0에서 확인해야 합니다.

## 6. 예전에 약 20 rpm으로 보였던 이유

지금 해석은 이렇습니다.

**약 19–20 rpm은 주로 vendor 호흡수 필드의 행동이지, AI가 20 rpm을 예측했다는 증거가 아닙니다.**

가장 깨끗한 대조 (2026-07-28 명시적 15 rpm 시험):

```text
메트로놈 목표:     약 15 rpm
breath_phase 추정: 약 15.01 rpm
vendor 평균:       약 18.80 rpm
vendor 중앙값:     약 19 rpm
```

12 rpm, 15 rpm, 20 rpm에서 vendor 오차가 같지 않습니다.
그래서 “항상 +N rpm 보정하면 된다”는 공식은 만들지 않습니다.

## 7. 현재 데이터로 무엇을 할 수 있는가?

지금 바로 하면 좋은 일:

1. 필드/펌웨어 계보 확인 (`breath_phase` vs `breath_rate_raw`)
2. `breath_phase` 값의 범위와 파형 모양 보기
3. 로그가 얼마나 자주 찍히는지 보기
4. 실제로 phase가 얼마나 자주 **새로** 갱신되는지 재구성하기
5. 같은 값이 반복되는 stale 구간 찾기
6. phase가 끊기는 dropout 보기
7. 거리 lock-loss / freeze 보기
8. paced 호흡의 주기 보기
9. vendor 호흡수가 phase와 얼마나 다른지 보기
10. 실패 조건을 QA 증거로 남기기
11. 기존 Phase-B 입력과 의미가 같은지 비교하기
12. 30초/300샘플 모델 입력을 **신선한 phase로** 만들 수 있는지 판단하기
13. 대응이 확인된 뒤에만, 탐색적으로 기존 모델을 돌려 보기
14. 나중에 라벨을 붙일 수 있는 세션과, 분석 전용으로만 둘 세션 가리기
15. 다음 측정 규약(M-C1) 설계하기

성적표를 못 낸다고 해서 쓸모없는 데이터가 아닙니다.

## 8. 왜 지금 데이터로 모델 정확도/F1을 계산하면 안 되는가?

시험에 비유하면 쉽습니다.

- 학생이 답안지(모델 출력)를 썼습니다.
- 그런데 채점 정답지가 없습니다.
- 이 상태에서 점수를 발표하면 안 됩니다.

센서 입력만으로는 “모델이 맞았는지”를 말할 수 없습니다.
그 순간 사람이 **실제로 어떤 호흡 상태였는지**라는 정답이 필요합니다.

```text
입력 X는 있음
정답 y가 불충분함
→ Accuracy / F1을 MR60 실센서 성능으로 발표하면 안 됨
```

기존 Phase-B 성적(예: Accuracy 약 0.56, Macro F1 약 0.495)은
**공개 데이터로 만든 offline 결과**입니다.
팀 MR60 로그의 점수로 바꿔 읽으면 안 됩니다.

## 9. 우리가 원래 모델을 만들 때 사용한 데이터는 무엇이 달랐는가?

Phase A/B에서 쓴 공개 mmWave 데이터는 “파형만 있는 폴더”가 아니었습니다.

같이 있었던 것:

- 레이더 관련 신호
- 사람 식별/그룹 정보 (110명, 녹음 440개)
- 실험 조건 (rest, post-exercise, 자발적 숨 참기 등)
- 클래스 의미 (`NORMAL`, `RAPID_OR_ABNORMAL`, `APNEA` 프록시)

그래서 30초 창마다 정답을 붙이고, 사람 단위로 학습/검증/테스트 셋을 나눌 수 있었습니다.

중요한 제한:

```text
APNEA = 실험용 자발적 숨참기 프록시
≠ 임상 수면무호흡 진단
```

A4 라벨 규칙의 핵심 (`MMWAVE_LABEL_MAPPING_PROFILE_001`):

- `NORMAL`: 휴식 조건 및/또는 Movesense 가슴 가속도 호흡수 10 이상 25 미만
- `RAPID_OR_ABNORMAL`: 참조 호흡수 25 이상이거나 10 미만 (느린 호흡)
- `APNEA`: 30초 창 안에서 숨 참기 표시가 6초 이상 겹치면 프록시 라벨

여기 나온 **25 bpm은 공개 데이터 Phase-A 라벨 의미(frozen evidence)** 입니다.
출처는
`datasets/mmwave/manifests/a4_label_pilot/label_mapping_profile.json` 의
`rapid_min_rr_bpm: 25.0` 이고, 매퍼
(`scripts/mmwave_label_mapper.py`)와 A4 validator
(`scripts/validate_mmwave_label_pilot.py`)가 같은 profile을 읽습니다.
이 숫자는 **Movesense 가슴 가속도계로 잰 참조 호흡수**에 대한 임계값이지,
메트로놈 cue나 MR60 `breath_rate_raw`에 대한 규칙이 아닙니다.

```text
Phase-A에서 RAPID가 Movesense 참조 RR >= 25 bpm 로 정의돼 있었음
≠
향후 MR60에서 25 bpm 이상이면 무조건 RAPID label
```

25 bpm을 다음 실측의 자동 라벨 임계값으로 복사하면 안 됩니다.
M-C1 라벨 규칙은 그 측정 규약에서 따로 정해야 합니다.

즉 예전 데이터는:

```text
입력 X + 충분히 정의된 정답 y
→ 지도 학습/평가가 가능했다
```

그 결과가 팀 MR60에서 바로 성립한다는 뜻은 아닙니다.

## 10. 현재 raw data로 학습은 불가능한가?

**불가능하지는 않습니다.**
“모든 머신러닝이 기술적으로 원천 차단됐다”는 뜻이 아닙니다.

다만 **지금 이 로그를 `NORMAL` / `RAPID_OR_ABNORMAL` / `APNEA` 프록시 재학습 데이터로 바로 쓰면 안 됩니다.**

이유:

- Phase-B 클래스 정답이 아직 없음
- 사람이 거의 `S001` 한 명
- 독립 호흡 참조 센서가 없음
- `breath_phase`가 기존 모델 입력과 같은 신호인지 미확인
- 로그 10 Hz가 신선한 phase 10 Hz인지도 미확인

그래서 지금은:

```text
먼저 M-C0 (장치 쪽 분석)
```

이지:

```text
바로 재학습
```

이 아닙니다.

비지도 학습이나 domain adaptation도 이론상 가능합니다.
하지만 **M-C 단계에서 하면 안 됩니다.**
그 방법은

```text
장치 차이를 측정하는 일
```

과

```text
그 차이에 맞춰 모델을 바꾸는 일
```

을 섞어 버립니다.
재학습/적응은 차이가 측정되고 **따로 승인된 뒤의 M-D**입니다.

## 11. paced 12/15/20 rpm을 바로 NORMAL/RAPID 라벨로 쓰면 안 되는 이유

절대 이렇게 자동 변환하지 마십시오.

```text
12 rpm → NORMAL
15 rpm → NORMAL
20 rpm → RAPID_OR_ABNORMAL
```

**시킨 호흡 속도**와 **Phase-B 클래스**는 다른 개념입니다.

예전 라벨은 원본 데이터셋의 실험 의미와 Movesense 참조 규칙에서 왔습니다.
우리가 새로 정한 rpm 컷이 아닙니다.

실제로 A4 규칙에서 `RAPID_OR_ABNORMAL`은 **공개 데이터의 Movesense 참조 호흡수**가
**25 rpm 이상**일 때입니다. 그래서 20 rpm cue를 잘 따라 쉬었더라도, *그 예전
계약만 놓고 보면* 자동으로 RAPID가 되지 않습니다.

이 25 bpm은 그 점을 설명하기 위한 frozen evidence이지,
“앞으로 MR60에서 25 이상이면 RAPID”라는 새 규칙이 아닙니다.

더 중요한 예: **12 rpm이라고 적힌 세션이 실제로는 약 6.06 rpm이었습니다.**

메트로놈은 대략 12 rpm을 치고 있었는데, 실제 가슴 움직임은 한 호흡에 약 10초,
즉 분당 약 6회였습니다. 안내를 절반으로 이해한 실패 사례입니다.

```text
시킨 호흡
≠
실제로 한 호흡
```

앞으로 기록할 때도 둘을 나눠야 합니다.

```text
INTENDED_CONDITION     (시키려고 한 것)
ACTUALLY_OBSERVED_REFERENCE  (실제로 관측된 것)
```

paced cue는 유용한 실험 메모입니다.
독립적으로 관측된 생리 정답과 같지는 않습니다.

## 12. 다음 실측에서는 무엇을 같이 기록해야 하는가?

원리만 적습니다. 자세한 측정 규약은 이후 M-C1 일입니다.

나중에 창마다 정답을 붙이려면 최소한 아래가 같이 있어야 합니다.

```text
MR60 신호 (breath_phase 또는 선택한 최저 노출 신호)
+
fresh timestamp / 얼마나 신선한지
+
사람 가명
+
세션 ID
+
트라이얼 ID
+
거리
+
자세
+
센서 방향/부착
+
필요하면 재실/움직임 맥락
+
미리 정한 실험 조건
+
가능하면 독립 호흡 reference
+
실제로 수행한 호흡 상태/속도
+
lock / dropout / 실패 여부
+
펌웨어/수집 코드 신원
+
시작·끝 시각
```

표로 보면:

| 같이 남길 것 | 왜 필요한가 |
| --- | --- |
| MR60 신호 | 모델 입력 후보 |
| 신선도(`phase_age` 등) | 같은 값을 반복 출력했는지 구분 |
| 사람/세션 ID | 학습·평가를 사람 단위로 분리 |
| 거리·자세·방향 | 같은 조건인지 재현 |
| 사전 정의 조건 | 무엇을 하려 했는지 |
| 실제 호흡 reference | 채점 정답 |
| 실패/dropout | 정상 세션과 섞지 않기 |

## 13. 왜 '정답'을 측정 시점부터 함께 기록해야 하는가?

신호만 모으면 센서 분석은 됩니다.
모델 학습/평가까지 가려면 **그 순간의 정답**이 신호와 같은 시간에 있어야 합니다.

```text
신호만
→ 센서 분석에 좋음

신호 + 믿을 수 있는 정답
→ 학습/평가를 지원할 수 있음
```

원리 예시일 뿐, 최종 실험 스케줄이 아닙니다.

```text
사람 S003
거리 / 자세 기록

00:00–02:00  미리 정한 NORMAL 조건
02:00–04:00  미리 정한 RAPID_OR_ABNORMAL 조건
04:00–...    미리 정한 숨참기(APNEA 프록시) 조건

MR60 신호와 독립 reference를 같이 녹음
```

숨참기는 기존 안전 규칙 안의 자발적 프록시일 뿐, 임상 무호흡이 아닙니다.
정확한 시간표·큐·안전 절차는 이 문서에서 정하지 않습니다.

12 rpm 실패 사례가 말하는 것도 같습니다.
나중에 “그 파일은 12 rpm이었다”고 기억에 의존하면 틀린 정답이 붙습니다.
**측정하는 그 순간에 의도/실제/실패를 같이 적어야** 합니다.

## 14. 여러 사람 데이터를 어떻게 모아야 하는가?

나중에 모델을 다시 다루게 되면, 사람 ID를 처음부터 남겨야 합니다.

```text
학습에 쓰는 사람
검증에 쓰는 사람
최종 테스트에 쓰는 사람
```

을 나눌 수 있어야 합니다.

같은 사람의 창이 학습과 테스트에 섞이면,
“새로운 사람에서도 된다”는 착각이 생깁니다.

이것은 이미 Phase A5에서 쓴 원칙입니다.
한 사람의 모든 녹음과 창은 하나의 분할에만 들어갑니다.

지금 전달 CSV는 `S001`만 보입니다.
파일 여러 개가 사람 여러 명을 뜻하지 않습니다.

## 15. 지금 데이터는 버리는 것인가?

아닙니다.

현재 데이터는

> 실제 MR60이 어떤 신호를 내보내고, 얼마나 자주 갱신되며,
> 언제 stale/freeze가 발생하고, vendor 호흡수가 phase와 어떻게 다른지

를 확인하는 데 **매우 가치가 있습니다.**

버리지 말고, 용도를 지키면 됩니다.

확인된 숫자 요약 (영문 보고서와 동일 근거):

```text
telemetry/log rows ≈ 9.99 Hz
fresh breath_phase cadence = 아직 미확립

breath_phase = phase-like 중간 신호
breath_rate_raw = vendor 호흡수

15 rpm cue:
  phase ≈ 15.01 rpm
  vendor 중앙값 ≈ 19 rpm
고정 +N rpm 보정은 불가

명목 12 rpm 실패 세션 ≈ 6.06 rpm

D15:
  vitals/phase freeze는 있음
  거리 표본 표준편차 ≈ 2.94 cm (0 아님)

전달 데이터 사람 다양성: S001
독립 호흡 참조: 없음
```

```text
현재 데이터로 할 수 있음:
센서/domain 분석
M-C0
fresh/stale/cadence 분석
Phase-B 입력 대응성 평가
실패조건 분석

현재 데이터로 바로 하면 안 됨:
정식 Accuracy/F1 발표
MR60 model validated 선언
즉시 supervised retraining
paced rpm을 임의로 Phase-B class에 매핑
```

